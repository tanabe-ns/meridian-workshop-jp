# 提案書: 在庫管理ダッシュボードのモダナイズ

**RFP 番号:** MC-2026-0417
**提出先:** Meridian Components, Inc. 調達部長 J. Okafor 様
**提出期限:** 2026年5月8日 17:00(米国中部時間)

---

## 1. エグゼクティブサマリー

Meridian Components のオペレーションチームは、日々の業務の起点である概要ページの数字を信用できず、表計算ソフトで集計し直しています。IT チームは自動テストがないために変更を承認できず、改善が止まっています。この2つが、現行システムの価値を引き出せていない根本原因だと理解しています。

私たちは、**「確実に進める」** ことを提案の軸に置きます。

- **最初の数週間で、現場の信頼を取り戻します。** 概要ページ(R1)を最優先で直し、期間や拠点を変えれば KPI が正しく動く状態を、最初のマイルストーンとして納品します。
- **続いて、変更を安全にします。** ブラウザテスト(R4)とアーキテクチャドキュメント(R5)を整備し、IT チームが以降の変更を承認できる土台を作ります。
- **その土台の上で、残りを進めます。** Reports の欠陥解消(R2)と発注推奨機能(R3)は、テストに守られた状態で進めます。
- **希望項目は、東京チームの課題に直結する国際化対応(D2)に絞って提案します。** UI のモダナイズ(D1)とダークモード(D3)は、今回は範囲に含めません。
- **価格は上限額付きの T&M とします。** R2 の欠陥件数が「少なくとも8件」で確定していないため、調査の結果に応じて工数を精算します。上限額は先に確定し、予算の予見可能性を担保します。進捗は各フェーズの終わりに、動くものと数字でご報告します。

### 2.2 R1 概要ページの改修

- **進め方:** 概要ページの各 KPI が、画面上部のフィルター(期間・倉庫・カテゴリー・注文ステータス)のどれを受け取り、どのデータで計算されているかを洗い出します。前任ベンダーの引き継ぎメモは、このページの不具合に触れていません。そのため、メモの記述は鵜呑みにせず、コードとの突き合わせから始めます。
- **リスク:** 原因が1か所とは限りません。画面側でフィルターを渡していない場合と、API 側で無視している場合の両方があり得ます。調査は最初の数日で区切り、結果を共有します。
- **完了基準:** すべての KPI が、4種のフィルターの選択を反映する。フィルターごとの期待値を一覧にし、バックエンドのテストとブラウザ上の操作の両方で確認する。

### 2.3 R4 ブラウザテストの自動化

- **進め方:** 主要なユーザーフローを、貴社と合意したうえで選定します(前提 A3)。選んだフローを、実際のブラウザを操作するテストにします。CI で実行できる形で引き渡します。
- **リスク:** 「主要」の範囲が広がると工数が膨らみます。フローの一覧を最初に合意することで防ぎます。
- **完了基準:** 合意したフローがすべて自動テストで通る。IT チームの手元で、手順書どおりに実行できる。

### 2.4 R5 アーキテクチャドキュメント

- **進め方:** 構成(Vue 3 + Vite、FastAPI、JSON ファイルによるデータ)、データフロー、フィルターの仕組み、起動方法、既知の課題を、コードから確認して記載します。形式は Markdown とします。
- **リスク:** 前任ベンダーのメモは不完全で、古い箇所もあります。記載内容はコードで裏取りします。
- **完了基準:** 新しく着任した IT 担当者が、このドキュメントだけでアプリを起動し、主要な構成を説明できる。

### 2.5 R2 Reports モジュールの改修

- **進め方:** まず、貴社が記録している8件以上の問題を受け取り、こちらの調査で見つけたものと突き合わせて一覧にします。件数と優先順位を合意したうえで、修正に着手します。
- **リスク:** 件数が確定していません。T&M の上限額内で収まらない場合は、追加の修正を協議します(前提 A4)。
- **完了基準:** 合意した一覧のすべての項目が解消され、それぞれにテストがある。

### 2.6 R3 発注推奨機能

- **進め方:** 現在の在庫水準、需要予測、オペレーターが指定する予算上限から、発注を推奨する Restocking ビューを追加します。推奨の計算ルール(安全在庫の考え方など)は、R. Tanaka 様のチームと短いワークショップで決めます。
- **リスク:** 需要予測データの品質が推奨の精度を左右します。データの不整合が見つかった場合は、先に共有します。
- **完了基準:** 予算上限を指定すると、倉庫ごとの推奨発注リストが表示される。合意したサンプルケースで期待どおりの結果になる。

### 2.7 D2 国際化対応

- **進め方:** 東京倉庫のスタッフが日常的に使う画面から、順に日本語表示に対応します。対象の画面は、R1〜R3 の納品物を含め、フェーズ4で合意します。
- **完了基準:** 合意した画面で、言語を切り替えられる。

## 4. スケジュール

契約開始日から数える目安です。具体的な日付は、契約日の確定後に置き換えます。

| フェーズ | 期間(目安) | 内容 | 成果物 |
|---|---|---|---|
| 1. 概要ページの修正 | 第1〜2週 | R1 の調査と修正 | KPI がフィルターに連動する概要ページ |
| レビューと予備 | 第3週 | 貴社のレビュー、承認、予備 | フェーズ1の受け入れ |
| 2. 安全な変更の土台 | 第4〜6週 | R4、R5 | ブラウザテスト一式、アーキテクチャドキュメント |
| レビューと予備 | 第7週 | 貴社のレビュー、承認、予備 | フェーズ2の受け入れ |
| 3. Reports の改修 | 第8〜10週(幅: 3〜5週) | R2 | 欠陥一覧と、解消済みの Reports |
| レビューと予備 | 第11週(幅の上限の場合は第13週) | 貴社のレビュー、承認、予備 | フェーズ3の受け入れ |
| 4. 新機能と国際化 | 第12〜15週(幅の上限の場合は第14〜17週) | R3、D2 | Restocking ビュー、日本語表示 |

全体で**約15週間**を目安とし、フェーズ3が幅の上限(5週)になった場合は**約17週間**です。

- **フェーズ3の期間は、幅で示しています。** R2 の欠陥件数は「少なくとも8件」で確定していないため、欠陥一覧に合意した時点で、期間を確定します(前提 A4)。期間が確定した時点で、以降のフェーズの日程を更新してお知らせします。
- **各フェーズの間に、1週間のレビューと予備を置いています。** 貴社での確認と承認の時間と、見込みを外したときの余裕を兼ねています。
- 各フェーズの終わりに、動くものを使ったデモと進捗の報告を行います。
