1. エグゼクティブサマリー

Meridian Components のオペレーションチームは、日々の業務の起点である概要ページの数字を信用できず、表計算ソフトで集計し直しています。IT チームは自動テストがないために変更を承認できず、改善が止まっています。この2つが、現行システムの価値を引き出せていない根本原因だと理解しています。

私たちは、「確実に進める」ことを提案の軸に置きます。

  • 最初の数週間で、現場の信頼を取り戻します。概要ページ(R1)を最優先で直し、期間や拠点を変えれば KPI が正しく動く状態を、最初のマイルストーンとして納品します。
  • 続いて、変更を安全にします。ブラウザテスト(R4)とアーキテクチャドキュメント(R5)を整備し、IT チームが以降の変更を承認できる土台を作ります。
  • その土台の上で、残りを進めます。Reports の欠陥解消(R2)と発注推奨機能(R3)は、テストに守られた状態で進めます。
  • 希望項目は、東京チームの課題に直結する国際化対応(D2)に絞って提案します。UI のモダナイズ(D1)とダークモード(D3)は、今回は範囲に含めません。
  • 価格は上限額付きの T&M とします。R2 の欠陥件数が「少なくとも8件」で確定していないため、調査の結果に応じて工数を精算します。上限額は先に確定し、予算の予見可能性を担保します。進捗は各フェーズの終わりに、動くものと数字でご報告します。

2.2 R1 概要ページの改修

進め方
概要ページの各 KPI が、画面上部のフィルター(期間・倉庫・カテゴリー・注文ステータス)のどれを受け取り、どのデータで計算されているかを洗い出します。前任ベンダーの引き継ぎメモは、このページの不具合に触れていません。そのため、メモの記述は鵜呑みにせず、コードとの突き合わせから始めます。
リスク
原因が1か所とは限りません。画面側でフィルターを渡していない場合と、API 側で無視している場合の両方があり得ます。調査は最初の数日で区切り、結果を共有します。
完了基準
すべての KPI が、4種のフィルターの選択を反映する。フィルターごとの期待値を一覧にし、バックエンドのテストとブラウザ上の操作の両方で確認する。

2.3 R4 ブラウザテストの自動化

進め方
主要なユーザーフローを、貴社と合意したうえで選定します(前提 A3)。選んだフローを、実際のブラウザを操作するテストにします。CI で実行できる形で引き渡します。
リスク
「主要」の範囲が広がると工数が膨らみます。フローの一覧を最初に合意することで防ぎます。
完了基準
合意したフローがすべて自動テストで通る。IT チームの手元で、手順書どおりに実行できる。

2.4 R5 アーキテクチャドキュメント

進め方
構成(Vue 3 + Vite、FastAPI、JSON ファイルによるデータ)、データフロー、フィルターの仕組み、起動方法、既知の課題を、コードから確認して記載します。形式は Markdown とします。
リスク
前任ベンダーのメモは不完全で、古い箇所もあります。記載内容はコードで裏取りします。
完了基準
新しく着任した IT 担当者が、このドキュメントだけでアプリを起動し、主要な構成を説明できる。

2.5 R2 Reports モジュールの改修

進め方
まず、貴社が記録している8件以上の問題を受け取り、こちらの調査で見つけたものと突き合わせて一覧にします。件数と優先順位を合意したうえで、修正に着手します。
リスク
件数が確定していません。T&M の上限額内で収まらない場合は、追加の修正を協議します(前提 A4)。
完了基準
合意した一覧のすべての項目が解消され、それぞれにテストがある。

2.6 R3 発注推奨機能

進め方
現在の在庫水準、需要予測、オペレーターが指定する予算上限から、発注を推奨する Restocking ビューを追加します。推奨の計算ルール(安全在庫の考え方など)は、R. Tanaka 様のチームと短いワークショップで決めます。
リスク
需要予測データの品質が推奨の精度を左右します。データの不整合が見つかった場合は、先に共有します。
完了基準
予算上限を指定すると、倉庫ごとの推奨発注リストが表示される。合意したサンプルケースで期待どおりの結果になる。

2.7 D2 国際化対応

進め方
東京倉庫のスタッフが日常的に使う画面から、順に日本語表示に対応します。対象の画面は、R1〜R3 の納品物を含め、フェーズ4で合意します。
完了基準
合意した画面で、言語を切り替えられる。

5.2 前提条件

RFP に記載がなく、見積もりに影響する点について、次のとおり前提を置きました。これらが異なる場合は、スケジュールと価格を見直します。ご質問の期限(4月28日)までに、確認事項として送付します。

A1. 予算: RFP に予算のレンジが記載されていないため、上記の T&M の上限額は、当社の見積もりに基づいて提示します。貴社のご予算に上限がある場合は、範囲を調整します。
A2. UI の「現在の標準」: D1 で言及されている「現在の標準」は定義されていません。このため、D1 は今回の提案の範囲に含めません。範囲に含める場合は、基準となるデザイン指針をご提示ください。
A3. 「主要なユーザーフロー」: R4 の対象は、貴社との合意で選定します。目安として、概要ページの確認、在庫の絞り込み、Reports の表示、Restocking での発注推奨の4〜5フローを想定しています。
A4. R2 の欠陥件数: 「少なくとも8件」とされている件数は、貴社の記録をいただいたうえで確定します。確定した一覧を超える追加分は、別途協議します。フェーズ3のスケジュール(3〜5週の幅)も、この一覧の合意をもって確定します。
A5. 環境とデータ: 現行のソースコードとサンプルデータを、このまま開発に使えることを前提とします。貴社側の検証環境や、担当者(R. Tanaka 様のチーム、IT 部門)への確認の機会をいただけることを前提とします。
